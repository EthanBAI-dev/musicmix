# 分析：预测被推翻了

## 1. 我预测错了

跑之前我在 `src/separation/postprocess.py` 的模块 docstring 里写下了一条**可证伪预测**：

> 掩码类后处理只能重新分配混音里已有的复数谱，天花板就是 IRM oracle。
> P1 实测 htdemucs 在 drums / bass 上已与 IRM oracle 统计上不可区分（p=0.88 / 0.18），
> 而 other 差 2.59 dB、vocals 差 2.31 dB 且显著。
> → **预测：软掩码 / MWF 在 other 和 vocals 上应当有增益，在 drums 和 bass 上不应当有。**

实测：

| 声部 | 预测 | 实测（软掩码） |
|---|---|---|
| other | **应当变好** | **-0.658 dB，显著变差** ❌ |
| vocals | **应当变好** | -0.371 dB，不显著 ❌ |
| drums | 应当不变 | -1.896 dB，显著变差 ❌ |
| bass | 应当不变 | -2.503 dB，显著变差 ❌ |

**四条全错。** 掩码细化不是"在有头寸的声部见效"，而是**在所有声部都是净损失**，
平均 -1.357 dB（95% CI [-1.642, -1.053]）。MWF 稍好但同样是负的，-0.923 dB。

## 2. 推理错在哪

错在这一步：我从"IRM oracle 比 htdemucs 高 2.59 dB（other 轨）"推出"所以掩码有 2.59 dB 的头寸"。

**这个头寸只有拿到真值幅度才够得着。** IRM oracle 用的是**真值**幅度算掩码；
而软掩码细化用的是**模型自己估计的**幅度。两者不是一回事：

- 掩码细化做的事情，本质是把估计**投影到"混音复数谱的实值缩放"这个集合**上
- 这个集合的最优点就是 IRM oracle = **8.95 dB**
- 而 htdemucs 的 base 已经是 **8.80 dB** —— **距离这个集合的天花板只剩 0.15 dB**

所以即便掩码估计得完美无缺，整体最多也只能涨 0.15 dB。
而实际的掩码来自模型自己不完美的幅度估计，落点远低于最优点，于是净亏 1.36 dB。

**一句话：投影到一个天花板只比你高 0.15 dB 的集合里，指望它带来 2.59 dB 的提升，这个推理从一开始就不成立。**

## 3. 一个佐证（注意：未经隔离实验证实）

P1 的 oracle 变体表里有一行值得重看（8 首曲目，uSDR）：

| 变体 | 平均 |
|---|---|
| IRM 功率掩码（真值幅度） | 9.23 |
| **真值幅度 + 混音相位** | **8.35** |

**即便幅度完全正确，只要被迫使用混音的相位，就只有 8.35 dB** —— 低于 htdemucs 的 base。
而所有掩码方法（实值掩码 × 混音复数谱）都必然继承混音的相位。

Demucs 是直接生成波形的，它能重建相位；掩码细化把这部分能力**丢掉了**。
这与 P1 的另一条结论一脉相承：htdemucs 在 drums/bass 上已与 IRM oracle 不可区分，
正是因为它不受掩码族的约束。

> ⚠️ **诚实标注**：上面这条是**机制推测**，支撑它的是 P1 已有的 oracle 变体数据，
> 而不是针对本次实验的隔离实验。要坐实"损失主要来自相位"，
> 应当单独测一次"保留模型幅度、只把相位换成混音相位"的中间态，
> 看它是否已经掉到软掩码的水平。这一步**尚未做**。

## 4. 真正有效的是什么

| 手段 | 平均 Δ | 显著 | RTF | 值不值 |
|---|---|---|---|---|
| ＋overlap 0.50 | +0.037 dB | ❌ | 0.066 → 0.084（+27%） | **不值** —— 整体不显著，只有 drums 单独显著 |
| ＋TTA(swap, flip) | **+0.095 dB** | ✅ **四轨全部显著** | 0.066 → 0.193（**×2.9**） | 真实但很小，代价近 3 倍 |
| ＋软掩码 | -1.357 dB | ✅ 变差 | 0.066 → 0.080 | **有害** |
| ＋多通道维纳 | -0.923 dB | ✅ 变差 | 0.066 → 0.094 | **有害** |

TTA 是本轮唯一的正结果，而且**四个声部全部显著变好**（bass +0.177 dB 最多），
方向非常干净 —— 符合它的原理：声道交换与极性翻转都是同变变换，
平均只抵消模型噪声、不引入偏差。

但要如实说：**+0.095 dB 换 2.9 倍推理时间，工程上不划算。**
放进作品集时应当这样呈现，而不是包装成"提升了 0.1 dB"。

## 5. 这一轮的真正产出

不是 +0.095 dB，而是**排除了一整条路线**：

1. **掩码类后处理在这个 baseline 上是死路。** 不是调 α、换 n_fft 能救的问题 ——
   天花板（IRM oracle 8.95）离 base（8.80）只有 0.15 dB，投影必亏。
   任何"再试试 α=1 / 加大 FFT"的想法都可以直接省下来。
2. **P1 那条"other 有 2.59 dB 头寸"的说法要加限定词**：那是**oracle 幅度**下的头寸，
   不是任何掩码方法可及的头寸。已回填进 P1 报告。
3. **剩下的路只能是"提升幅度/波形估计本身"**，也就是：
   - 更强的单模型（`htdemucs_ft`，官方 9.20 dB）
   - 多模型集成（不同模型的误差不相关，平均才有意义）
   - 微调 / 蒸馏（路线 B / C）

   —— 这些都不是"推理期免费午餐"，都要真金白银的算力。
