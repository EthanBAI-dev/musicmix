# 产品计划：把作品集做成一个可用的学习型产品

> **定位：学习用途，非商业。**
> 因此 CC-BY-NC 许可的模型与数据集（MERT、MuQ、MUSDB18、MTG-Jamendo、MoisesDB）都可以用 ——
> 前提是守住三条：**不收费、注明出处、不再分发数据集里的音频**。
>
> 本计划所有外部数字均来自调研时（2026-09）核实过的来源，见文末。
> **论文数字不能直接和我们的数字比**：训练数据和评测口径可能不同，换进来之前必须在本项目自己的评测框架上复测。

---

## 0. 三条结论

1. **最值得换的三个模型**：分离（htdemucs → SCNet XL / BS-RoFormer）、表征（MERT → MuQ，正好补 P9 发现的乐器短板）、曲式（自写 → All-In-One，能给出真正的 verse / chorus）
2. **最值得改的架构**：**模型可插拔**（统一接口，换模型不动业务代码），以及**浏览器端分离**（已有人用 ONNX + WebGPU 跑通 htdemucs）
3. **纪律不变**：每次换模型都在自己的框架里复测、跑之前写预测。本项目的教训是 7 个改模型的改动 6 个无效 —— **更强的论文模型不等于在我们这里更好**

## 1. 现状 vs 当前先进方案

| 模块 | 现在用的 | 现在成绩 | 先进方案 | 公开成绩 | 换过来能得到什么 |
|---|---|---|---|---|---|
| **分离** | htdemucs（**仓库 2025-01-01 已归档停更**） | cSDR 8.80 dB（自己复现） | **SCNet XL IHF**（仅 MUSDB18HQ 训练） | 平均 10.08（bass 9.23 / drums 11.81 / vocals 11.42 / other 7.88） | 更干净的四轨；且换掉一个不再维护的依赖 |
| | | | **BS-RoFormer**（SDX'23 冠军） | 加 500 首额外数据后 11.99 | 质量上限；Mel-RoFormer 在人声/鼓/其他上更好 |
| **节拍** | librosa 动态规划 + 自写小节线相位 | 合成演示曲 8/8（**不是真实基准**） | **beat_this**（ISMIR 2024） | 已发表方法中拍点/小节线 F1 最好，无需 DBN 后处理 | 真实音乐上的可靠拍点；代码和权重都是 MIT |
| **曲式** | 递归矩阵 + 谱聚类 | 只能给 A / B / C | **All-In-One** | 约 30 万参数，同时输出节拍、小节线、段落 | **真正的段落名**：intro / verse / chorus / bridge / solo / outro 等 |
| **和弦** | 24 个三和弦模板 | 合成演示曲 8/8 | **BTC**（ISMIR 2019） | 支持大词表（七和弦等） | 大词表和弦 —— **但仓库不发权重，得自己训** |
| **表征 / 标签** | MERT-95M 冻结 | mAP 0.288（只用 9.9% 数据） | **MuQ**（腾讯） | MARBLE 上几乎全面超过 MERT，**乐器分类尤其明显** | 直接对准 P9 最弱的乐器类（提升倍数仅 3.5×） |
| **检索** | MERT 嵌入 + 精确检索 | R@10 0.139（随机 14 倍） | **MuQ-MuLan** / **CLAP** | 文本↔音乐联合嵌入 | **新能力：用文字搜歌**（MuQ-MuLan 支持中文："忧伤的钢琴"） |

> ⚠️ **SCNet 的 10.08 与我们的 8.80 不能直接相减。** 两者都只用 MUSDB18HQ 训练、测同一个测试集，
> 但 ZFTurbo 报的「SDR」与我们用的 museval 中位数聚合 cSDR **未必同口径** ——
> 本项目 P1 已经吃过"中位数聚合与均值聚合结论相反"的亏。换进来后必须用 `run_separation_eval` 复测。

## 3. 架构优化点

### 3.1 模型可插拔（最优先，其他一切的前提）

现在 htdemucs、MERT 是**写死在业务代码里**的。定义三个接口：

```
Separator.separate(audio) -> {vocals, drums, bass, other}
Analyzer.analyze(audio)   -> {bpm, beats, downbeats, key, chords, sections}
Embedder.embed(audio)     -> 向量
```

现有实现变成其中一个后端；新模型作为另一个后端并排存在。好处有两个：
- 换模型**不改业务代码**
- 同一个评测框架能**并排比较**新旧后端 —— 这正是本项目最擅长的事

### 3.2 浏览器端分离

> **更正**：之前 M9 部署计划写过"htdemucs 的 ONNX 导出出了名的难搞，WASM 远慢于实时，不建议"。
> **这个判断是错的** —— [demucs-web](https://github.com/timcsy/demucs-web) 已用 ONNX Runtime Web + WebGPU/WASM 纯前端跑通 htdemucs，
> [StemSplit/demucs-onnx](https://github.com/StemSplit/demucs-onnx) 也解决了 htdemucs_ft 的导出问题。

意义：**分离完全在用户浏览器里做**，不需要服务器、不上传音频（隐私）、可以直接部署到 GitHub Pages。
代价：用户要下载约 100 MB 权重，速度取决于用户显卡。

### 3.3 服务端：之前的一个决定要翻转

之前选择"标准库 HTTP 服务 + 全局串行锁、不引任务队列"，理由是**单机自用**。
**多人同时用时这个理由不再成立**，需要补：

- **内容哈希缓存**：同一首歌不重复分离（分离是最贵的一步）
- **任务队列与并发上限**：避免多个请求同时抢显存
- **结果存储与过期清理**

仍然可以保持轻量，不必一上来就 Celery + Redis。

### 3.4 分离一次，多处复用

All-In-One **自己内部就会先做一次 demucs 分离**。若曲式和分离各跑一遍，就是重复计算。
接口设计上让分析直接吃分离结果。

### 3.5 换模型要有回归保护

把 `build_summary` 接进"换模型"的流程：每换一个后端，自动重跑评测、生成对比表。
防止"换了更强的模型、但数字其实没涨"却没人发现。

## 4. 分阶段计划

> 时间是粗估，按你每周能投入的时间调整。**每个阶段都先写预测、再动手**。

### 阶段 0 · 可插拔重构（约 1 周）

- **目标**：只改结构，不改效果
- **交付**：`Separator` / `Analyzer` / `Embedder` 三个接口；现有实现迁移为默认后端
- **验收**：现有 240 条测试全过；SUMMARY 里**所有数字一个都不变**
- **风险**：重构引入静默行为变化 —— 所以验收标准是"数字完全不变"，而不是"测试通过"

### 阶段 1 · 分离升级（约 2 周）

- **目标**：接入 [ZFTurbo 框架](https://github.com/ZFTurbo/Music-Source-Separation-Training)，把 SCNet XL IHF 与 BS-RoFormer 作为新后端
- **预测（跑前写死）**：同口径 cSDR 相对 htdemucs **提升 ≥ 0.5 dB**，配对 bootstrap 显著
- **验收**：用本项目 `run_separation_eval` 在 MUSDB18HQ 测试集 50 首上复测；同时报 RTF（更强的模型可能慢得多）
- **风险**：论文数字与我们口径不同，实际提升可能远小于 10.08 − 8.80

### 阶段 2 · 分析升级（约 2 周）

- **目标**：beat_this 替换节拍；All-In-One 替换曲式，**第一次能标出 verse / chorus**
- **关键缺口**：目前节拍和弦只在**合成曲**上测过（8/8）。**这不是真实基准**。
  要用公开标注（如 [beat_this_annotations](https://github.com/CPJKU/beat_this_annotations)）在真实音乐上测
- **验收**：真实数据上，新旧节拍器的 F-measure 并排对比
- **风险**：All-In-One 依赖 NATTEN / madmom；MP3 解码有 20~40 ms 时间偏移，官方建议先转 WAV

### 阶段 3 · 表征升级（约 2 周）

- **目标**：MuQ 替换 MERT，按原协议 5 种子重跑
- **预测**：**乐器类提升倍数上升**（P9 基线 3.5×）
- **验收**：同种子配对比较，5/5 方向一致
- **必须提防**：P6 的教训 —— 特征变了，**头部的最优选择可能跟着变**。
  窗口段数、头部结构都要重验，不能直接沿用 MERT 下的结论

### 阶段 4 · 新能力（约 2 周）

- **文字搜歌**：MuQ-MuLan（支持中文）或 CLAP
- **浏览器端分离**：走 demucs-web 路线，部署到 GitHub Pages
- **验收**：文字搜歌需要**人工抽查**（代理指标说明不了"搜得准不准"）

### 阶段 5 · 需要你亲自做的（持续）

- **人工听审**：失败案例、检索结果、hiphop → drummachine 疑似漏标
- **P10 层级补全实验**（已预注册，随时可恢复）

## 5. 和 Moises 的区别

[Moises](https://stemsplit.io/blog/moises-ai-review) 有 3000 万以上用户，功能是分离 + 和弦 + 调性 + 变速变调 + 歌词 + 节拍器。
**学习型产品不该跟它比功能数量**，比的是它不做的事：

- **每个结果都说清楚可信度**：小节线置信度、调性的相对大小调备选、段落不编造名字
- **失败公开**：失败案例能在页面上 A/B 听，负结果写进 README
- **结论可复现**：每个数字都能从脚本重新生成

## 6. 不做什么

- **不商业化、不收费**
- **不在公开仓库或公开演示里放数据集音频**
- **不照搬论文数字**：一切以自己框架复测为准
- **不为追先进而堆模型**：本项目 7 个改模型的改动 6 个无效，先测再换
