# 架构审查与云端训练方案

审查日期：2026-09-12。对象：本仓库实际代码，基线提交 `60435a1`。这是定向代码审查与训练管线改进，不是安全渗透测试、法律意见或全量论文复现。

## 一、结论：作品集有价值，不能原样作为公司生产系统

Claude Code 做出的不是纯 API 网页壳：仓库有自己的评测、数据管线、标准分类头训练、检索实现、浏览器混音和失败案例分析。这些值得保留。模块化、真值与估计分开、用户曲目不伪造 SDR、分析失败不抹掉成功分离结果，都是合理设计。

但它目前更接近**研究型单用户原型**：依赖别人预训练的核心模型，实验结论有过度归因，缺少企业服务边界，且重要权重/数据有非商业限制。不能据此承诺商用、规模化稳定性或“自研音乐大模型”。判断标准是代码与证据，不是代码由 Claude 还是人写。

求职定位建议：**音乐信息检索/音频机器学习工程项目**。核心贡献是数据与评测协议、微调实验、性能/成本分析和可靠推理管线，而不是宣称发明 Demucs、MERT 或普通 MLP。

## 二、实际有哪些模型和管线

| 环节 | 当前实现 | 是否自己训练 | 边界 |
|---|---|---|---|
| 四轨分离 | `src/separation/demucs_model.py`，预训练 htdemucs | 此服务使用现成权重 | 分出 vocals/drums/bass/other，不等于任意单乐器分离 |
| 分离学生模型 | `src/separation/student.py` 的频谱复数掩码 U-Net；`colab/distill.ipynb` | 有训练实验入口，不能仅凭文件存在认定训练成功 | 教师输出不是干净真值；要做学生与教师的质量/延迟对照 |
| 音乐标签 | 冻结 MERT-95M/330M + mean/attention pooling + MLP等头部 | 旧实验训练头部，不更新 MERT | 标签、概率，不是音乐生成或分轨模型 |
| BPM/拍点/调性/和弦 | `src/analysis/` 的 librosa与模板方法 | 主要不是监督学习模型 | 24种大/小三和弦覆盖有限，真实歌曲需独立验证 |
| 段落结构 | chroma拍同步、自相似矩阵、谱聚类 | 无监督分组 | 相似段A/B/C不等于语义副歌/主歌 |
| 检索 | MERT/头部表征 + 精确余弦与简化 IVF | 表征部分可由标签监督得到 | 索引召回与人听起来相似不是同一目标 |
| Web | 原生 JavaScript + Web Audio | 无训练 | 增益/静音/独奏/EQ/导出主要是信号处理 |
| 服务 | 标准库 HTTP + 内存任务表 + 后台线程 | 无训练 | 单机原型，不是持久化分布式队列 |

实际上传任务 `src/service/jobs.py` 串联分离与节拍/和弦/结构分析；它**没有在此任务中调用音乐标签头或检索索引**。有离线实验模块不代表上传→所有AI功能已端到端接通。

推荐依赖关系不是所有任务排一条长队：

```text
上传 → 校验/统一音频与任务ID
          ├─ 四轨分离 → 混音器素材
          ├─ 原曲标签/嵌入 → 标签与检索结果
          └─ 节拍/调性/结构 → 分析结果
```

只有某个算法明确需要分轨（例如部分结构分析方案）时，才让它依赖分离。并行依赖不等于在同一块GPU上无限并发，GPU工作应受队列与显存预算管理。

## 三、优先修正的问题

### P0：商业授权与服务隔离——上公司环境之前

1. **商业许可不能用“不收费”来判断。** MERT-v1-330M 模型卡标注 CC-BY-NC-4.0。MuQ代码MIT，但公开权重也是CC-BY-NC-4.0。企业内部用于业务收益也不能自动假定满足非商业用途。微调不自动清除限制。[MERT模型卡](https://huggingface.co/m-a-p/MERT-v1-330M)、[MuQ官方许可](https://github.com/tencent-ailab/MuQ#license)
2. Jamendo代码Apache-2.0、元数据CC-BY-NC-SA-4.0、音频还需逐曲核对许可；官方数据集说明限定非商业研究/学术用途，其他用途要Jamendo书面授权。旧文档“音频与元数据一律不可再分发”“权重未声明也直接打勾可用”都过于简单。公开求职演示应使用合成或明确授权的音频，不能把“用户上传”当作版权证明。[数据集官方许可](https://github.com/MTG/mtg-jamendo-dataset#license)
3. `scripts/serve.py` 静态目录是仓库根目录，继承标准库目录浏览和文件服务。绑定公网时可能暴露 `.git`、数据、结果等；默认localhost是有益防护，但不是生产安全边界。应改成仅暴露明确的web静态目录与授权素材接口。
4. `src/service/jobs.py:submit` 每个请求创建线程，任务无限存内存；`_RUN_LOCK`只串行执行，不限制排队数量。200MB单请求上限不是总内存/磁盘配额。缺鉴权、租户隔离、任务持久化/取消、上传时长与解码资源约束、过期清理策略。
5. 上传输出目录只由文件名slug决定，同名上传可覆盖旧结果。要改为不可碰撞任务ID，文件名仅作显示字段。`web/app.js` 的曲目选择通过字符串插入 `innerHTML`，应统一改用文本节点/安全DOM构造；本次未做攻击验证，不宣称已确认可利用XSS。

本次没有把开发服务器改成生产服务器；上述风险尚未修复。不要通过 `--allow-remote` 直接暴露现有服务。

### P1：实验可信度——比再加一个模型更重要

1. **随机种子位置错误（本次已修）。** `scripts/train_tagging.py` 原来先构建随机初始化头部，再在 `src/tagging/train.py:train` 设置seed。旧5种子不等于完整控制初始化的5种子；本次将seed提前到构建前。旧结果保留，但需标注协议缺陷并重跑关键对照。
2. **样本集合变化。** `src/datasets/jamendo.py:load_split` 按块目录存在过滤，不能保证每个音频存在；旧训练脚本又按可用特征删样本，stem配置可能额外删歌。不同配置必须共享明确的曲目清单和标签顺序，不能只看样本数接近。
3. **测试集被反复用于看结果和规划实验。** 即使阈值只在验证集调，仍可能形成实验层面的测试泄漏。旧成绩不是一次性盲测。今后验证集选模型，最终测试独立命令；另加未参与选择的跨数据集/人工标注留出评估。换一个官方split也不自动消除历史接触，需查曲目和艺人交集。
4. **“5/5上涨”不是通用显著性检验。** 种子方差与歌曲采样不确定性是不同东西。报告同曲目配对置信区间、逐类指标、每类正样本支持数、多个seed；多项消融需要预先指定主比较，不能挑最好的结果事后宣称成立。
5. 换基座、隐藏维度、层选择、片段长度、训练轮数/早停规则同时变，不能把差异全归因于模型大小。冻结特征涨不动**不代表微调也一定无效**；ASL下降也不能简单解释为“它只改变校准”。结论应限于实际实验配置。
6. `src/retrieval/index.py:ExactIndex.search` 默认对查询矩阵对角线排除“自己”，只有查询与库同顺序时成立；外部上传曲目默认调用会错误排除无关歌曲。`k == 库大小` 时 `argpartition(..., k)` 也越界。生产接口应显式传query ID/self index并校验k。当前全库自检结果不能据此判为全错，但接口泛化有问题。
7. `src/analysis/structure.py` 强制将第一/最后一段叫intro/outro；位置不是音乐语义证据，一首歌可以直接从副歌开始。应改为中性标签，或使用有监督结构模型。合成歌曲上的通过率不能代替真实音乐准确率。
8. 蒸馏notebook里的“7dB等于教师80%”不合理：dB是对数单位，不能直接做百分比能力保留率。用SDR差值、实际试听和速度/资源比报告；学生不保证更快，必须测。

### P2：运维与可复现性

旧依赖未锁版本，项目限制Python `<3.12`，当前Colab不一定满足；MERT使用远程代码且未固定revision。新训练管线独立依赖文件、固定模型SHA、保存运行环境，但不把本机测试当云端兼容性证明。
缓存还应编码模型revision、预处理版本和数据版本；需要明确哪些数组是归一化之前/之后，避免静默混用。
公司部署还要结构化日志、监控、p50/p95延迟、GPU峰值、失败率、每首成本、重启恢复、模型版本回滚、权限与数据保留规则。

## 四、成熟模型如何参考，而不是只追“最新”

截至本次核对，以下是值得做同口径对照的成熟公开方案；不是对所有2026论文的穷尽排名，也不宣称接入后必然提升。

| 任务 | 候选 | 接入建议 |
|---|---|---|
| 音乐标签表征 | [MuQ官方实现](https://github.com/tencent-ailab/MuQ) | 作为MERT后的强对照。公开权重训练数据与论文最佳设定不同，不能照搬论文成绩；官方还建议推理FP32避免NaN，不能盲目套本次MERT的FP16设置 |
| 音乐/文本检索 | [MuQ-MuLan](https://github.com/tencent-ailab/MuQ) | 面向“忧伤的钢琴”一类文字搜歌，与现有音频相似检索是新增任务，需要音文配对评测 |
| 四轨分离 | [BS-RoFormer](https://arxiv.org/abs/2309.02612)、[Mel-Band RoFormer](https://arxiv.org/abs/2310.01809) | 先统一声部定义、训练数据和SDR聚合方式；有些公开权重仅做人声/伴奏，不能直接替换四轨接口；逐checkpoint查授权 |
| 节拍/小节线 | [Beat This!](https://github.com/CPJKU/beat_this) | 优先于继续加拍点启发式。代码与公开权重MIT，但官方仍提醒训练数据权利需评估 |
| 语义段落 | [All-In-One](https://github.com/mir-aidj/all-in-one) | 能预测verse/chorus等功能标签；应测错误率和耗时，不能因模型输出语义词就认定语义正确 |

本次先落地MERT微调，而不是同时替换五个组件：你已有MERT实验资产，可以建立“同基座冻结 vs 微调”的直接对照；之后加MuQ时才能知道收益来自训练策略还是换基座。保留现有Demucs基线，不因为仓库年代就否定已验证的功能。

## 五、这次交付与实验安排

新文件：`scripts/cloud_train.py`、`scripts/cloud_download.py`、`colab/train_mert.ipynb`、`colab/requirements-train.txt`、`colab/README.md`、`tests/test_cloud_training.py`。

1. **全量数据准备**：00–99全部下载到你指定的Drive目录，保留tar，完整保存嵌套split文件，失败停止且保留半成品。
2. **64首冒烟**：实际音频→MERT→BCE→反向传播→checkpoint。只确认工程能跑，不用于正式性能报告。
3. **全量冻结基线**：95M、10秒随机训练片段、验证三段、固定末层、MLP、BCE。
4. **只改变可训练参数范围**：95M最后两层微调，相同数据/采样/头部/验证；记录可训练参数、耗时和mAP。若改善不稳，用验证集试基座学习率，不能靠测试选。
5. **三种子复验**：冻结与微调各0/1/2。之后才考虑全量微调、330M或MuQ，分开比较，不一口气叠加。
6. **最后测试与端到端接入**：冻结验证阈值，导出每首预测；核对线上预处理与训练一致，再把best模型接进上传任务。新checkpoint尚未自动替换旧Web使用的模型。

新脚本训练时每首歌每轮取一段，评估多段取平均概率；不是将全曲一次送入Transformer。它避免全量音频塞进RAM，但直接读Drive tar仍可能I/O受限，须先测GPU利用率再决定本地分片暂存。

## 六、公司落地门槛与求职展示

内部研究验证：先确认机构用途符合授权，再在受控环境使用，可作为技术验证原型。
生产业务：当前不应直接上线。至少先通过授权确认、真实场景质量验收、安全与数据隔离、负载/恢复测试四道门槛；并不是换成FastAPI就自动合格。

推荐最终展示：

- 分离：固定50首评测口径、按声部SDR、失败试听、实时因子（处理耗时/音频时长）、峰值显存。
- 标签：全量数据准确样本数、mAP、MacroF1、逐类支持数、冻结/微调消融、3种子结果。
- 检索：明确“相关”的定义，区分语义Recall@K与近似索引Recall；过滤同曲和必要的同艺人泄漏。
- 产品：用户上传真实曲目的一条成功流程与一条失败/恢复流程，而非只展示合成演示数据。
- 贡献：基于开源预训练模型完成任务微调与可复现评测，解释失败案例与工程权衡；注明AI辅助开发，不将标准组件包装成原创模型。
