### 2026-07-29 · [P0][坑] SI-SDR 把"什么都没输出"判成了满分

**做了什么**
修复 `si_sdr` 在估计全零时返回 `+inf` 的 bug。

**现象 → 原因 → 解法**
- **现象**：`silence` 基线跑到落盘阶段 `KeyError: 'SI-SDR'`。
- **排查**：`aggregate` 会用 `isfinite` 过滤非有限值。silence 的四轨 SI-SDR 全被过滤 → 该指标整个消失 → 脚本取键时崩。往上追，发现每一轨的 SI-SDR 都是 `+inf`。
- **原因**：`si_sdr` 里写了 `if noise_energy == 0: return inf`。但估计全零时 `target` 和 `noise` **同时**为零 —— 这不是"完美吻合"，是"什么都没输出"，应该是**最差**而不是最好。
- **解法**：区分两种残差为零的情况：`target_energy > 0` 才是 `+inf`，否则 `-inf`。顺手让脚本对"某指标整体缺失"优雅降级 —— 注明原因，而不是崩溃或假装有值。

**结果**
`test_si_sdr_of_silent_estimate_is_negative_infinity` 钉住。测试 108 条全绿。

**下一步**
M0 收尾，写自检报告。

### 2026-07-29 · [P0][坑] BSS Eval 的 SIR/SAR 在合成数据上退化成垃圾值

**做了什么**
重写合成数据生成器（`src/datasets/synthetic.py`），修掉一个**看起来像评测 bug、实际是数据问题**的坑。

**现象 → 原因 → 解法**
- **现象**：IRM oracle 在合成数据上，cSDR=17.73 dB、ISR=22.50 dB 都正常，但 **SIR = -104 dB、SAR 恒为 0.00 dB**。
- **排查**：第一反应是 `museval.evaluate` 返回值解包顺序写错了。读源码确认是 `SDR, ISR, SIR, SAR`，我的写法没问题。排除代码后转向数据。
- **原因**：BSS Eval v4 把估计投影到"全部参考经 **512 阶 FIR 滤波**"张成的子空间上再做分解。而第一版合成数据：① 声部是**纯正弦**——一个 2 阶 FIR 就能把它变成同频率的任意相位/幅度；② 立体声用 `np.roll` 做**纯延迟**——纯延迟本身就是一个 FIR 抽头，左右声道线性相关。两条叠加让投影的最小二乘问题严重病态。
- **解法**：每个声部改为含**带限噪声**（宽带随机，FIR 无法预测）+ **音高随时间游走**（破坏同频正弦可互换的退化）+ 立体声靠**独立去相关噪声**而非延迟。

**结果**
修复后 SIR=26.43 dB（高于 SDR 19.89，符合预期）、SAR=21.52 dB。
加了回归测试 `test_oracle_sir_and_sar_are_sane`，断言"SIR 必须高于 SDR、SAR/ISR 必须是正常正值"。

顺带一个漂亮的验证：`trivial` 基线的 **SIR ≈ SDR 而 SAR = 145 dB**。完全符合物理直觉——混音本来就在参考张成的空间里，所以误差 100% 来自干扰、0% 来自算法伪影。这个"形态"比绝对数值更能说明评测是对的。

**教训（值得反复提醒自己）**
**指标异常时，先怀疑数据是否落在指标的适用假设之外，再怀疑指标实现。**
这次 SDR/ISR 一切正常、只有 SIR/SAR 崩了，极具迷惑性——如果只报 SDR，这个问题会一直潜伏。

**下一步**
把合成器从脚本里挪进 `src/datasets/`，让测试和评测脚本共用同一份数据。

### 2026-07-29 · [P0] 评测框架建成，108 条单测全绿

**做了什么**
完成 M0 全部内容：环境、仓库骨架、四个评测模块 + 显著性检验 + 性能测量，以及能一条命令跑出 SDR 表的 CLI。

**为什么这么做 / 选型理由**

1. **conda 环境用 Python 3.11 而不是 base 的 3.13。**
   madmom / demucs / NATTEN 这些 P2/P3 要用的 MIR 库在 3.13 上兼容性普遍不好，3.11 是这个生态的甜点位。现在多花 10 分钟建环境，比第 6 周被依赖地狱卡住划算。
   （踩了个小坑：沙箱里 conda 的 shell 函数包装器被拦，报 `__conda_exe: permission denied`，用 `/opt/anaconda3/bin/conda` 绝对路径就正常。）

2. **加了"合成数据"模式。**
   MUSDB18-HQ 有 30GB，不该让 M0 的验收卡在下载上。`--synthetic N` 现造几首玩具歌，30 秒就能验证整个评测链路。事实证明这个决定很值——上面两个 bug 都是在合成数据上抓到的。

3. **三个锚点：silence / trivial / oracle。**
   它们的正确值在解析上是已知的，所以能反过来验证评测代码。真实模型的成绩必须落在 trivial 和 oracle 之间。

4. **`(n_samples, n_channels)` 作为全项目波形约定。**
   跟 soundfile / museval / musdb 一致。torchaudio 用的是反过来的 `(ch, n)`，所以每次和 torch 交互都显式转置，不靠记忆。

5. **检索指标里 HitRate 和 Recall 分开命名。**
   文献里 "Recall@K" 至少有两种互不兼容的定义。本项目的代理真值（共享 ≥3 标签）会让每个查询有成百上千个相关项，两种口径的数值能差两个数量级。与其含糊，不如两个都算、分开命名。

**结果 / 数字**

环境：`music-mix` (Python 3.11.15) / torch 2.13.0 / MPS 实测 2779 GFLOPS 且与 CPU 结果零偏差 / museval 0.4.1 / librosa 0.11.0 / ffmpeg 8.1

三个锚点（合成数据 ×6，每首 5s）：

| 模型 | uSDR 平均 | cSDR 平均 | 说明 |
|---|---|---|---|
| silence | **0.00** | — | ✅ 精确等于解析值 |
| trivial | -6.83 | -6.81 | 下界 |
| oracle | 18.51 | 19.89 | 上界 |

测试：**108 passed**，覆盖 `eval/{separation,tagging,retrieval,stats}`、`audio/io`、`bench/timer`。

复现命令：
```
python -m scripts.check_env
python -m pytest tests/ -q
python -m scripts.run_separation_eval --synthetic 6 --synthetic-seconds 5 --model oracle --out results/m0_selfcheck_oracle.md
```

**踩的坑**
见上面两条独立记录。另外一个小的：`silence` 基线无法算 cSDR —— BSS Eval v4 要求估计非全零，否则投影方程组欠定。这是指标的固有约束不是缺陷，脚本改成自动跳过并说明原因。真实数据上也会遇到（有些歌本来就没有人声轨），所以 `evaluate_track` 里也做了 catch + 警告 + NaN 的处理，绝不静默吞掉。

**下一步**
M1：下载 MUSDB18-HQ → 先在真实数据上重跑三个锚点（预期 trivial 的 cSDR 在 0 dB 上下、oracle 在 12~15 dB）→ 再跑 htdemucs，目标复现 ~9.0 dB，误差 ≤ ±0.3 dB。

### 2026-07-29 · [P0][决策] 立项、技术调研与大纲成型

**做了什么**
确定项目范围与架构，完成开源方案调研，产出五份文档：总体大纲、术语表、方案调研与选型、评测协议、里程碑排期。

**为什么这么做 / 选型理由**

核心判断：**这个项目的价值在于"每个环节都有可复现的数字"和"至少三处是自己训/改的"**，而不是把开源模型串起来。所以定了三条原则：

1. **不从零训练任何大模型**。BS-RoFormer 级别的分离模型需要 8×A100 跑一周，本机 M2 Max 做不到，而且从零复现没有增量价值。资源集中投在两处：分离的**推理期改进 + 微调 + 蒸馏**，标签的**自研分类头 + 不平衡处理 + Stem-aware 融合**。
2. **评测代码先于模型代码**。没有可信评测的"改进"都是自我感动，所以 M0 的验收标准是"能对平凡基线跑出合理的 SDR"，而不是"跑通了某个模型"。
3. **找一个原创点把项目前后两半连起来**。定为 **Stem-aware Tagging**：先分离再分别提特征做标签，并提出可证伪的假设 H2（收益主要来自乐器类标签）。这是本项目最有辨识度的部分，成本低、闭环完整、正负结果都有价值。

调研结论（详见 [02-方案调研与选型](02-方案调研与选型.md)）：
- 分离：`htdemucs` 作主 baseline（~9.0 dB），RoFormer 系作强 baseline 与蒸馏教师（+1.3 dB 左右，bass 提升尤其显著）；训练/推理/评测统一走 ZFTurbo 的 Music-Source-Separation-Training 框架
- 分析：`beat_this` + `all-in-one`，**明确不自研**，把预算留给分离和标签
- 标签：基座全程**冻结**（MERT / MuQ，Essentia EffNet-Discogs 保底），只训头部
- 检索：FAISS + 弱监督度量学习，代理真值用"共享 ≥3 标签"

**踩的坑**
暂无实操坑。**已预判的三个高风险点**（写进 [00-总体大纲](00-总体大纲.md) §7 并配了降级方案）：
